# C++ 流式重建类平面专项测评报告

日期：2026-08-07

测试对象：`setc/build_live_observer/Release/omnivggt_stream_server.exe`
测试主题：类平面表面上的 C++ 流式重建精度、速度、资源占用和历史一致性

## 一、摘要

本次测试在 TUM Photometric Depth Super-Resolution 数据集的 blanket 类平面表面上进行。C++ 动态 bucket 主方案完成了 5 帧流式回放，总耗时 4,355.319 ms，平均 871.064 ms/帧，完整吞吐 1.148 FPS；固定 `pair-letterbox` 备选方案总耗时 5,166.974 ms，平均 1,033.395 ms/帧，吞吐 0.968 FPS。动态方案后续实际执行模型帧的平均总耗时为 1,381.687 ms，较固定方案的 2,095.615 ms 降低约 34.1%，说明动态 ROI 的收益已经在 C++ 流式路径中体现。

两种方案的类平面点云精度基本一致。动态方案在 61,687 个共同有效点上的三维 RMSE 为 181.2 mm，约为参考平均深度的 3.00%，参考深度 AbsRel 为 2.410%，δ<1.05 为 92.14%，δ<1.10 和 δ<1.25 均为 100%。固定方案的三维 RMSE 为 182.5 mm，约为 3.02%，AbsRel 为 2.405%。动态方案没有引入可见的精度退化，同时将 GPU 峰值从固定方案的 7,801 MiB 降至 7,454 MiB。

## 二、测试背景和项目改进目标

针对沙面、织物、墙面等连续缓变表面，现有通用流程主要存在多帧融合容易产生重影或分层、逐帧深度尺度不一致、边界直接拼接形成接缝、遮挡和删点造成孔洞、黑边误判为表面边界以及每帧完整推理导致重复计算严重等问题。本项目的类平面流式链路针对性地解决了这些问题，并将重点放在连续表面保持、局部更新和变化不足时的跳帧上。具体实现已经在项目的其他设计和代码文档中说明，本报告只记录最终测评结果。

正文以动态 bucket 为主方案，固定 `pair-letterbox` 为备选方案。动态方案用于验证 ROI 动态尺寸是否真正降低 C++ pair 推理开销；固定方案用于提供一个输入形状固定、部署简单、可随时回退的对照结果。

## 三、测试数据和基本口径

测试使用 TUM Photometric Depth Super-Resolution 数据集的 `xtion_blanket_sf2_sfs` 子场景，实际下载文件约 15.1 MB，没有下载大型完整序列。该表面具有纹理和连续缓变起伏，适合用于本项目的类平面专项测试，但不是数学无限平面。测试序列由一张真实表面图像生成 5 帧受控单应回放，输入和生成参数保存在 `stream_omnivggt_outputs/cpp_benchmark/dataset_cache/tum_photometric_blanket/planar_stream_input/`。

测试硬件为 NVIDIA GeForce RTX 5060 Laptop GPU，总显存 8,151 MiB；运行时为 LibTorch 2.7.0 CUDA 12.8、OpenCV 4.10.0 和 MSVC 19.29.30159。两种方案使用相同输入、首帧模型、BF16/CUDA 环境和前后处理流程，动态方案使用 518×700 上界 bucket，固定方案使用 700×700 pair 输入。

本报告中的 reference depth 来自数据集的 `z_est` 表面估计文件，不是独立激光或结构光真值。因此 AbsRel、深度 RMSE 和 δ 指标表示与参考表面的相对一致性；PLY 坐标还经过归一化，不能直接解释为未经校准的米制绝对点云误差。点云精度同时使用共同像素位置的三维点到点误差和归一化最佳平面残差进行评价。

## 四、测试结果和分析

### 4.1 配准、更新和输出状态

动态方案在第 1 至第 4 帧上都成功完成单应配准。后续帧的单应内点数平均为 393.75，范围为 334–445；重投影误差平均为 0.11275 px，范围为 0.101–0.121 px，最大误差为 0.121 px。这说明在本次受控的类平面运动中，锚帧画布与后续帧之间的二维配准稳定，没有出现明显的配准发散。

动态方案 5 帧中有 3 帧执行模型，2 帧由于变化区域不足而跳过模型，完整序列跳帧率为 40%，后续帧的跳帧率为 50%。最终 `VersionStore` 保留 92,685 个有效点，清洗后的 PLY 包含 84,289 个点。PLY 点数少于历史状态点数，是因为导出阶段还执行了窄孔洞填补、边界裁剪、局部异常清理和表面正则化，并不表示流式历史丢帧。动态方案历史记录包含 5 帧和 5 个 delta，`latest_version=5`，回放校验得到的最新哈希为 `16618848639565797231`。

固定方案在同一输入序列上也保留 92,685 个有效点，5 帧历史状态和更新点数与动态方案一致，历史校验哈希为 `4536601731698089429`。这说明两种方案的主要差异确实集中在后续模型输入形状和推理速度，而不是流式状态更新逻辑。

### 4.2 类平面点云精度

动态方案最终 PLY 与参考表面投影后共有 61,687 个共同有效对应点。在这些对应点上进行全局尺度/偏置对齐后，同像素三维点到点 MAE 为 150.8 mm，RMSE 为 181.2 mm，P95 为 339.4 mm，P99 为 407.3 mm。参考平均深度为 6.036 m，因此三维 RMSE 约占平均深度的 3.00%，P95 约占 5.62%。动态方案的 PLY 最佳平面 RMSE 为 0.021592，MAE 为 0.019106，P95 为 0.034874，P99 为 0.037695，均处于当前归一化坐标单位下的较小范围。作为参照，数据集 reference surface 本身的最佳平面 RMSE 为 0.229197 m，P95 为 0.435715 m，说明测试表面并非严格数学平面。

动态方案拟合得到的参考深度关系为

$$
d_\mathrm{ref}=-2.57369\,z_\mathrm{ply}+6.03753
$$

其中的负号来自当前 PLY 深度轴的归一化方向，不代表模型输出了负物理深度。按参考深度指标统计，动态方案 AbsRel 为 2.410%，深度 MAE 为 145.6 mm，深度 RMSE 为 174.9 mm，P95 为 330.0 mm，P99 为 388.6 mm；δ<1.05、δ<1.10 和 δ<1.25 分别为 92.14%、100.00% 和 100.00%。因此，在本次类平面回放中，92.14% 的点落在 5% 相对深度误差以内，全部点落在 10% 以内。

固定 `pair-letterbox` 方案的共同有效点为 62,347 个，同像素三维点到点 MAE、RMSE、P95 和 P99 分别为 150.5 mm、182.5 mm、346.8 mm 和 430.2 mm；三维 RMSE 约为参考平均深度的 3.02%。固定方案的参考深度 AbsRel 为 2.405%，参考深度 RMSE 为 175.8 mm，δ<1.05、δ<1.10 和 δ<1.25 分别为 91.30%、100.00% 和 100.00%；其 PLY 最佳平面 RMSE 为 0.022753。两种方案的精度处于同一水平，动态输入没有带来可见的精度退化。

从点云角度看，本次结果可以评价为较好，但这个结论的适用范围是“经过尺度/偏置对齐后的相对表面一致性”。动态方案的三维 RMSE 约为平均深度的 3.00%，P95 约为 5.62%，且没有出现大范围深度发散或明显分层；这说明本项目的锚定配准、深度对齐、软融合和支撑修复在当前类平面流上共同发挥了作用。由于参考深度不是独立绝对真值，不能据此直接宣称米制绝对点云误差达到了同样水平。

### 4.3 速度和动态尺寸迁移效果

动态方案的 5 帧总处理时间为 4,355.319 ms，平均 871.064 ms/帧，折算完整回放吞吐为 1.148 FPS。5 帧的总耗时依次为 1,260.635、1,566.407、1,196.966、166.549 和 164.762 ms；对应的模型耗时依次为 416.184、1,052.994、1,021.943、0 和 0 ms。第 3、4 帧没有执行模型，因此它们的时间主要用于二维对齐、变化检测和状态维护。

动态方案去掉首帧后，帧 1–4 的平均处理时间为 773.671 ms/帧，约为 1.293 FPS。帧 1、2 是后续实际执行模型的帧，其平均总耗时为 1,381.687 ms/帧，平均模型耗时为 1,037.469 ms/帧；跳过模型的帧平均耗时为 165.656 ms。5 帧总耗时的中位数为 1,196.966 ms，按 5 个样本线性计算的 P90 为 1,444.098 ms。

从阶段分解看，动态方案 5 帧的图像读取总计 149.645 ms，二维对齐总计 464.857 ms，变化检测总计 37.247 ms，模型阶段总计 2,491.121 ms，深度对齐总计 49.582 ms，增量 patch/融合总计 275.313 ms。模型阶段占总时间约 57.20%，是主要瓶颈，但其占比已经明显低于固定输入方案。

固定方案的同序列总处理时间为 5,166.974 ms，平均 1,033.395 ms/帧，完整吞吐为 0.968 FPS；重复运行得到约 0.92–0.97 FPS。固定方案逐帧总耗时为 632.062、2,210.946、1,980.283、171.722 和 171.961 ms，模型耗时为 537.515、1,698.894、1,788.603、0 和 0 ms。去掉首帧后平均为 1,133.728 ms/帧，约 0.882 FPS；帧 1、2 的后续模型执行总耗时平均为 2,095.615 ms/帧，模型阶段平均为 1,743.749 ms/帧，跳过模型帧平均为 171.842 ms。固定方案模型阶段占总处理时间约 77.90%。

因此，动态 bucket 使后续模型平均耗时从固定方案的 1,743.749 ms 降至 1,037.469 ms，下降约 40.5%；后续实际执行模型帧的平均总耗时从 2,095.615 ms 降至 1,381.687 ms，下降约 34.1%；完整 5 帧吞吐从 0.968 FPS 提升至 1.148 FPS，提升约 18.6%。这证明此前“ROI 已经变小，但 C++ 仍然使用固定 700×700 pair 输入”的迁移缺口已经解决，动态尺寸的收益已经传递到了 C++ TorchScript pair 推理。

需要特别区分首帧模型时间和后续帧总时间。首帧使用单帧 700×434 模型，后续帧则使用当前图像与 anchor 的双帧 pair 模型，同时还要执行单应配准、ROI 构造、深度对齐和融合。因此，动态 ROI 可以明确降低后续 `model_ms`，但不能仅凭重建点数减少就要求每个后续 `total_ms` 都低于首帧。Python 版附录也显示了同样现象：后续模型阶段比首帧快，但后续整帧总时间仍可能因为配准和融合开销而更长。

### 4.4 资源占用和两种方案的取舍

动态方案在 250 ms 采样下的 GPU 峰值为 7,454 MiB，占 8,151 MiB 总显存的约 91.4%；C++ 进程工作集峰值约为 3,917.6 MB。固定方案 GPU 峰值为 7,801 MiB，占总显存约 95.7%；进程工作集峰值约为 1,824.1 MB。动态方案由于模型输入从 700×700 降至 518×700，GPU 峰值降低了约 4.3 个百分点，显存余量更好；但动态 bucket 的 TorchScript/JIT 缓存和 C++ 运行时状态使当前主机工作集更高。固定方案的主机内存优势明显，但显存峰值已经更接近 8 GB 上限。

综合取舍后，推荐将动态 bucket 作为默认方案：它的精度与固定方案相当，速度更高，GPU 余量更大，适合本项目需要利用局部变化区域的主要场景。固定 `pair-letterbox` 作为备选方案保留：当部署环境不便携带动态模型目录、希望只管理一个后续模型文件，或更重视主机内存和输入形状确定性时，可以直接使用固定方案。若未来使用多个动态 bucket，应在获得更小 padding 收益的同时重新评估模型文件、缓存和显存预算。

## 六、论文使用限制

本次 5 帧序列由一张真实类平面表面图像经过已知单应变换生成，不是原始真实相机视频，所以结果主要说明类平面配准、局部更新、动态推理、融合和跳帧链路的工作状态。`z_est` 是数据集提供的 reference surface，不是独立激光或结构光真值；AbsRel、RMSE 和 δ 指标经过全局尺度/偏置对齐，只能作为相对表面深度一致性。由于当前 PLY 深度经过归一化，若论文需要报告绝对 Chamfer、绝对点到面误差或真实尺度法向误差，还需要让 C++ 输出带有相机内参和尺度的坐标，并使用独立测量真值。

5 帧样本量也不足以给出稳定的均值和方差。正式论文应在多个纹理、不同倾角、不同运动幅度和更多真实连续帧上重复测试，并报告 mean±std、P50/P90、跳帧率、模型执行率、GPU 峰值和主机内存。当前动态方案显存峰值约占 8 GB 的 91.4%，固定备选约占 95.7%；提高分辨率、增加模型分支、部署更多动态 bucket 或扩大队列前，都需要先进行显存预算。

## 七、结论

在当前类平面专项测试中，动态 bucket 方案已经完成从 Python 逻辑到 C++ 流式 TorchScript pair 路径的迁移验证。它在保持与固定方案相近点云精度的同时，将完整 5 帧吞吐从 0.968 FPS 提升到 1.148 FPS，将后续模型执行帧的平均总耗时降低约 34.1%，并将 GPU 峰值占用从约 95.7% 降至约 91.4%。固定 `pair-letterbox` 方案则作为输入形状固定、文件管理简单、主机内存较低的可靠备选。两种方案都已经完成同一类平面序列上的精度、速度、资源和历史一致性记录，可根据部署条件选择使用。

OmniVGGT 流式点云实时观察与交互式回放：具体项
目实现方案
一、最终实现目标
项目最终拆分为两个独立进程：
1. omnivggt_stream_server.exe ：负责持续接收图像、执行差异检测与模型推理、更新权威点云状态、
生成增量记录、保存历史并向客户端实时发布。
2. omnivggt_live_viewer.exe ：负责实时渲染点云、保持最新状态、独立重建历史状态、控制帧时间轴
以及执行三维旋转、缩放和平移。
系统运行后具有以下确定语义：
• 每接收到一张输入图像，就生成一个单调递增的 frame_seq 。
• 每次真正修改点云状态，就生成一个单调递增的 commit_version 。
• 时间轴以 frame_seq 为单位，而不是绝对时间。
• 用户停留在历史帧时，后端输入、推理、点云更新和 live_head_frame 继续推进。
• 用户点击“返回实时”时，不重新加载数据，而是直接切换到持续维护的 LiveState 。
• 用户切换帧时，三维观察相机不重置，仍可在同一观察视角下比较不同帧。
• 每一个历史帧都可以确定性地恢复到当时的点云状态。
• 当前帧发生变化的点可以高亮，必要时还可以同时显示更新前和更新后的点。
核心架构固定为：

 ↓

二、对当前代码的准确判断
2.1 当前代码为什么只能在输入结束后看到点云
当前 omnivggt_stream.cpp 的主循环确实逐帧执行推理和融合，但是在整个循环结束以后才调用：
write_canvas_ply(out_dir / "stream_pointcloud.ply", canvas, args);
也就是说，目前所谓“流式”仅发生在推理和 CanvasState 更新层面，输出层仍然是离线的。循环内部没有任
何以下机制：
• 点云提交事件；
• 增量点云数据；
• 实时发布接口；
• 非阻塞渲染线程；
• 历史状态记录；
• 帧到点云版本的索引。
因此，不能通过简单地每帧重新写一个 PLY 来真正解决问题。那样不仅开销大，而且无法支持可交互时间轴和
实时状态与历史状态解耦。
2.2 当前流式状态本质上是 2.5D 深度画布
当前 CanvasState 存储的是：
cv::Mat rgb_f;
cv::Mat depth;
cv::Mat conf;
cv::Mat weight;
cv::Mat valid;
cv::Mat support;
每个首帧画布像素对应至多一个深度值。最终写 PLY 时，三维坐标通过下面的方式得到：
px = normalized_pixel_x;
py = normalized_pixel_y;
pz = canvas.depth[y][x];
因此，当前流式路径并不是一个可以任意插入和删除无序三维点的通用点云，而是一个固定分辨率的、首帧坐
标系下的二维栅格深度场，也就是典型的 2.5D 点云。
2
这并不妨碍实现用户要求的三维旋转和时间回放。相反，固定的 518×518 像素槽位使第一版实现更简单、更稳
定：每个像素天然就是一个永久稳定的 point_id ，不用立即引入复杂的三维哈希表、KD-tree 或动态点分配
器。
本方案因此明确采用：
point_id = y * canvas_width + x
对于 518×518 输入，总槽位数恒定为：
268324 个 point slot
每个槽位在不同帧中可以是有效、无效或被更新，但槽位编号永远不变。
2.3 当前代码并没有真正只对差异区域节省模型计算
当前流程先计算 change_mask ，但只要变化比例超过 no_change_ratio ，仍然执行：
Prediction pred = run_model(module, frame, ...);
传入的是完整当前帧。 change_mask 只在后面的 fuse() 中限制哪些像素被写入 Canvas，并不会减少
TorchScript 模型的计算量。
因此必须区分两个概念：
• 增量点云更新：当前代码已经部分实现，只修改掩码内的状态。
• 增量神经网络计算：当前代码尚未实现，模型仍然运行完整 518×518 输入。
本项目的实时可视化系统不依赖模型是否真正实现 ROI 级加速，但为了与设想的“差异点合成新图后单独推
理”一致，推理输入需要改为锚点坐标下的差异合成图。
2.4 当前融合语义是加权平均，不是替换
当前 fuse() 使用：
new_depth = (old_depth * old_weight + observation * new_weight)
/ total_weight;
RGB 也使用相同的加权平均方式。这与“差异区域推理后替换原点云”并不完全一致。
如果场景中的物体发生移动，加权平均可能留下拖影、旧表面或深度中间值。具体实现中应将更新策略改为：
• 对于静态重复观测，可以保留轻微融合；
• 对于被 change_mask 明确判定为变化的区域，默认执行替换；
• 旧状态必须被保存到 Delta 中，以支持向后回放。
3
因此，新的核心操作不再叫 fuse() ，而叫：
build_replacement_patch()
apply_patch()

四、核心数据模型
4.1 帧编号与提交版本
必须同时维护两个编号。
using FrameSeq = std::uint64_t;
using CommitVersion = std::uint64_t;
frame_seq 表示输入顺序。任何接收到的输入图像都必须获得一个编号，即使该帧最终未运行模型。
5
commit_version 表示权威点云状态修改次数。只有成功应用一个 Patch 后才递增。
例如：
frame_seq: 100 101 102 103 104 105
commit_version: 81 82 82 83 83 84
status: OK OK SKIP OK SKIP OK
帧 102 没有变化，因此它对应的点云状态仍然是版本 82；但时间轴仍然存在帧 102。
帧索引定义为：
enum class FrameStatus : std::uint8_t {
Received,
Aligning,
DiffReady,
Inferencing,
Committed,
NoChange,
Coalesced,
Failed
};
struct FrameRecord {
FrameSeq frame_seq;
CommitVersion base_version;
CommitVersion commit_version;
FrameStatus status;
float changed_ratio;
float align_error_px;
std::uint32_t changed_point_count;
std::uint32_t valid_point_count;
std::string image_name;
};
4.2 点槽位状态
由于当前 Canvas 是固定二维栅格，不必在第一版使用通用稀疏三维点结构。
CPU 侧使用 SoA：
struct CanvasState {
int width = 518;
int height = 518;
6
std::vector<float> depth;
std::vector<float> confidence;
std::vector<std::uint32_t> rgba;
std::vector<std::uint32_t> last_update_frame;
std::vector<std::uint8_t> valid;
cv::Mat anchor_rgb_u8;
cv::Mat canvas_rgb_f;
cv::Mat support;
AnchorCamera anchor_camera;
CommitVersion version = 0;
};
推荐让 cv::Mat 只用于图像处理阶段。权威点云状态的深度、置信度和颜色应逐渐迁移到连续 std::vector
中，因为：
• 更适合序列化；
• 更适合快照；
• 更适合生成 GPU 数据；
• 不依赖 OpenCV 的引用计数和步长；
• 更容易进行精确前后版本比较。
锚点相机记录为：
struct AnchorCamera {
float fx;
float fy;
float cx;
float cy;
float depth_scale = 1.0f;
float depth_bias = 0.0f;
};
三维位置不必在 CPU 中永久存储，可以由像素槽位和深度即时计算：
X = (x - cx) / fx * Z;
Y = -(y - cy) / fy * Z;
Z = depth;
这样既比当前归一化 x/y 更符合透视几何，也能减少日志和网络负载。
4.3 单点前后状态
为了支持时间轴向前和向后逐帧播放，每次变化必须记录旧值和新值。
7
struct SlotValue {
float depth;
float confidence;
std::uint32_t rgba;
std::uint32_t last_update_frame;
std::uint8_t valid;
};
struct SlotDelta {
std::uint32_t slot_id;
SlotValue before;
SlotValue after;
};
单帧点云增量：
struct PointCloudDelta {
FrameSeq frame_seq;
CommitVersion from_version;
CommitVersion to_version;
std::vector<SlotDelta> changes;
float changed_ratio;
std::uint32_t valid_point_count;
bool scene_jump;
};
存储 before 和 after 的直接收益是：
apply_forward(delta):
state[slot_id] = after
apply_backward(delta):
state[slot_id] = before
因此，当用户在相邻帧间拖动时，不需要每次从快照重新构建。
4.4 Patch 的二维分块
为了避免将成千上万个离散槽位分别上传 GPU，将 Canvas 划分为 32×32 的 Tile。
8
tile_x = x / 32
tile_y = y / 32
tile_id = tile_y * tile_count_x + tile_x
518×518 最终得到约 17×17 个 Tile。
每个 Delta 构建时同时统计：
std::vector<std::uint32_t> dirty_tile_ids;
CPU 侧仍然逐点应用 Patch；GPU 更新时则以 Tile 为单位上传连续数据。这样可以把数千次小型 OpenGL 调用
变成十几次或几十次连续更新。
五、对现有推理流程的具体改造
5.1 重构 Prediction
当前 Prediction 只保留：
cv::Mat depth;
cv::Mat conf;
而 TorchScript 模型实际输出五个张量：
pose_enc
depth
depth_conf
world_points
world_points_conf
新的定义为：
struct Prediction {
cv::Mat depth;
cv::Mat depth_conf;
float fov_h;
float fov_w;
// 主要用于调试和算法验证，不作为首版权威状态。
torch::Tensor world_points_cpu;
9
torch::Tensor world_points_conf_cpu;
};
首帧推理完成后，从 pose_enc 中获得 FOV，计算锚点相机内参：
fy = (height * 0.5f) / tan(fov_h * 0.5f);
fx = (width * 0.5f) / tan(fov_w * 0.5f);
cx = width * 0.5f;
cy = height * 0.5f;
如果实际模型的 pose_enc 语义与 omnivggt_edge.cpp 中一致，可以直接复用该文件的解析代码。
5.2 增加差异合成输入
现有代码先把当前图像 warp 到首帧 Canvas：
warped_rgb_f = warp(current_frame, H_current_to_anchor);
之后新增：
cv::Mat build_inference_composite(
const CanvasState& canvas,
const cv::Mat& warped_current_rgb,
const cv::Mat& change_mask,
const cv::Mat& valid_warp);
合成规则：
首帧：
 composite = frame.rgb
后续帧：
 composite = canvas 当前 RGB
 change_mask 内替换为 warped_current_rgb
 新出现且 valid_warp 有效的区域替换为当前 RGB
伪代码：
cv::Mat composite = canvas.canvas_rgb_f.clone();
warped_current_rgb.copyTo(composite, change_mask);
模型随后直接处理锚点坐标系下的 composite ，输出的深度天然对应锚点 Canvas，因此不再需要先对原图推
理、再对深度进行 Homography warp。
10
需要明确：固定形状 TorchScript 模型仍然运行完整 518×518 计算。差异合成保证的是状态语义和输出一致
性，而不是自动减少网络 FLOPs。若论文声称模型计算量也按变化区域下降，则还需要另外改造模型或实现
ROI 推理；但这不会影响实时观察与回放系统。
5.3 将 fuse() 替换为两阶段提交
当前 fuse() 同时承担状态修改和融合，无法获得修改前的状态，也无法构造可重放 Delta。
改为：
CandidatePatch build_replacement_patch(
const CanvasState& current,
const cv::Mat& inferred_depth,
const cv::Mat& inferred_conf,
const cv::Mat& composite_rgb,
const cv::Mat& update_mask,
FrameSeq frame_seq,
const Args& args);
然后由唯一的提交器调用：
PointCloudDelta commit_patch(
CanvasState& state,
CandidatePatch&& patch);
构造 Patch 时，不立即修改 Canvas：
for each pixel in update_mask:
read before state
construct after state
append SlotDelta
变化区域的默认更新逻辑为：
if new_depth valid and confidence >= min_conf:
after.depth = new_depth
after.confidence = new_confidence
after.rgba = new_color
after.valid = true
else if region is explicitly confirmed removed:
after.valid = false
else:
do not create SlotDelta
对于用户描述的“替换”，变化区域不再使用旧权重累积：
11
after.depth = inferred_depth;
after.color = current_color;
after.confidence = inferred_confidence;
可在边缘区域增加短距离羽化，但不能对整个变化区域继续无限加权平均，否则动态物体容易产生拖影。
5.4 无变化帧也必须提交时间轴记录
当前代码在 skip_model 时什么都不更新。新的逻辑是：
if changed_ratio <= no_change_ratio:
append FrameRecord {
frame_seq,
base_version = current_version,
commit_version = current_version,
status = NoChange
};
publish FrameStatusMessage;
不生成点云 Delta，但时间轴继续向前。
六、服务器端具体线程模型
服务器进程采用四条逻辑链路，但只有一个线程可以修改权威点云。
6.1 FrameSource 线程
当前 list_images() 在启动时列出固定数量的文件，不支持持续输入。替换为：
class FrameSource {
public:
virtual std::optional<RawFrame> next() = 0;
};
第一版实现 DirectoryFrameSource ：
• 启动时读取已有图片并排序；
• 之后持续监听目录；
• 新文件大小和修改时间连续两次扫描不变后才认为写入完成；
• 每个文件只处理一次；
• frame_seq 由系统分配，不依赖文件名；
• 新图片进入容量有限的输入队列。
12
Windows 下可以先使用 20–50 ms 周期的 std::filesystem 扫描。目录监视不是系统性能瓶颈，无需一开始
接入复杂的原生文件系统事件 API。
6.2 InferenceWorker 线程
推理线程严格串行运行当前 TorchScript 模块：
Frame
 → preprocess
 → align
 → diff
 → composite
 → model
 → depth alignment
 → CandidatePatch
LibTorch 模型和 CUDA 上下文只由该线程持有。
推理线程不直接写权威 Canvas，只产生：
struct CandidateCommit {
FrameRecord frame;
CandidatePatch patch;
StreamMetrics metrics;
};
并将其送入 Commit 队列。
6.3 CommitWorker：唯一写者
CommitWorker 是整个系统唯一可以修改 CanvasState 、 commit_version 和历史索引的线程。
处理顺序：
接收 CandidateCommit
 ↓
检查 base_version
 ↓
为 Patch 分配 to_version
 ↓
应用到权威 CanvasState
 ↓
构造含 before/after 的 PointCloudDelta
 ↓
写入 append-only 日志
 ↓
更新 frame index
13
 ↓
必要时写 Snapshot
 ↓
发布给网络订阅者
这里必须保证：
磁盘日志成功写入以后，才对客户端发布新版本
否则服务器崩溃后可能出现客户端曾经看到、但服务器无法恢复的版本。
6.4 Publisher 线程
提交完成的 Delta 使用不可变对象发布：
std::shared_ptr<const PointCloudDelta>
每个客户端拥有独立的有限队列。慢客户端不得阻塞 CommitWorker。
若客户端队列溢出：
停止给该客户端继续塞入逐帧 Delta
发送 ResyncRequired
要求客户端重新加载最新 Snapshot
这比无限积压更合理，因为实时观察首先要求跟上最新状态，而不是让服务器被一个卡顿客户端拖慢。

deltas.bin 按提交版本追加：
struct DeltaRecordHeader {

std::uint32_t crc32;
};
后面是 Zstd 压缩的 SlotDelta 数组。
deltas.idx 保存：
struct DeltaIndexEntry {

std::uint64_t file_offset;
std::uint32_t record_size;
};
这样可以按版本直接定位，而不必扫描整个日志。
7.3 Frame 索引
frame_index.bin 保存每个 frame_seq 对应的版本：

而不是假设一帧一定对应一个点云版本。
7.4 Snapshot
每隔 60 个有效提交版本生成一个快照，或者累计 Delta 大小超过阈值时提前生成。
快照保存完整数组：
depth[N]
confidence[N]
rgba[N]
last_update_frame[N]
valid[N]
anchor_camera
commit_version
518×518 的完整状态即使不压缩也只有数 MB，生成和加载都很轻，不需要首版就实现复杂的三维分块快照。
7.5 回放恢复算法
Seek 到目标帧 f ：
v = frame_index[f].commit_version
s = 最大且满足 snapshot.version <= v 的快照
加载 snapshot s
顺序应用 delta(s+1 ... v)
相邻帧拖动时不重新加载快照：
向前一帧：apply_forward(delta)
向后一帧：apply_backward(delta)
只有用户进行大跨度跳转时才执行快照重建。

9.5 Seek 任务取消

时间轴快速拖动期间可以继续显示最近完成的历史状态；用户停止拖动后再完成目标帧的精确重建。

10.5 变化观察

十二、输入速度高于推理速度时的处理
用户要求时间轴按输入帧继续向前，因此不能简单地让输入线程阻塞到推理结束，也不能悄悄丢弃帧。
输入队列容量建议设置为 2 或 3。队列满时执行最新帧优先的合并策略：
frame 100 正在推理
frame 101 在等待
frame 102 到达
frame 103 到达并导致队列满
此时：
• 保留最新待处理帧 103；
• 帧 102 记录为 Coalesced ；
• 帧 102 的时间轴状态映射到当时最近的已提交版本；
• 系统继续处理 103。
时间轴上仍然有帧 102，但明确知道它没有独立点云提交。
这保证：
• 输入时间持续推进；
• 系统不会出现无限延迟积累；
• Viewer 不会假装每一张输入都已经产生了独立几何结果。

十三、断线、重连和恢复
13.1 Viewer 重连
Viewer 保存：
last_live_version
last_live_frame
重新连接时向服务器发送：
我当前拥有版本 V
如果服务器仍保留 V+1...current 的 Delta，直接补发。
如果对应 Delta 已经不在内存缓存中，则服务器发送：
ResyncRequired(latest_snapshot_version)
Viewer 加载最新 Snapshot，再继续接收实时 Delta。
13.2 Server 重启
服务器启动时：
1. 加载最后一个完整 Snapshot；
2. 从 Snapshot 版本后顺序重放 deltas.bin ；
3. 校验 CRC；
4. 恢复 CanvasState 、 commit_version 和 frame index；
5. 再开始接收新输入。
因此历史回放不依赖进程一直存活。

十八、该方案最关键的三个实现决定
第一，不要继续把 PLY 当成实时状态格式。PLY 只在运行结束或用户手动导出时生成；实时更新必须使用内存
状态和二进制 Delta。
第二，当前代码应优先利用固定 518×518 Canvas 的稳定槽位，而不是立即实现通用的动态三维点云哈希。这
样可以用较低复杂度完成确定性回放、双状态和 GPU 局部更新。当前算法本身仍然是首帧坐标下的 2.5D 重
建，系统结构必须如实反映这一点。
第三，实时状态与历史状态必须是两份独立状态：
LiveState：永远追赶服务器最新版本
PlaybackState：只响应用户当前查看帧
时间轴只控制 PlaybackState，绝不能控制推理循环或 LiveState。这一条是实现“我正在查看历史，但输入时
间仍然继续向前”的根本条件。
完成上述结构以后，整个工程的工作方式就是：
输入图像持续到达
→ 模型持续产生局部变化
→ 权威点云按版本提交
→ Viewer 中最新点云实时变化
→ 所有提交同时形成可逆历史
→ 用户可以像播放视频一样拖动帧时间轴
→ 任意时间点都可以自由旋转和观察三维点云
